# DERT: commands share their application evidence

Authority: the user's 2026-09-09 future-proofing instruction names DERT as the
ecosystem/executable, normalizes ERPDERT's operational role to `update`, adds
`where`, and defines `--doctor` / `-dr`. Features and language structures remain;
MER and other targeted proprietary names retain their purpose. This decision
supersedes older command examples without rewriting original source artifacts.

## Person and actual interaction

A person asks where an application lives, sees which route wins, understands
other installations and their folders, and can follow the selected installation
into manager checks and a deliberate repair. The connected evidence should make
a confusing machine understandable, with the existing restrained MER composition.

`DERT update codex` preserves the initial discovery entry into the update module.
`DERT update codex updateme` retains the existing explicit npm rehearsal.
`DERT where codex` locates command routes and application-adjacent folders.
`DERT where <application>` can find other valid application names; update and
repair capabilities remain adapter-specific, never inferred from an executable.
`DERT where codex --doctor` (also `-dr`) diagnoses the selected copy, verifies the
manager and offers a concrete reinstall proposal when supported. `--path` chooses
an exact discovered launcher. Package changes require a proposal-bound `--apply`
token; merely locating or requesting a diagnosis never uninstalls an application.

The normalized UDL uses existing slots:

```DERT
STERT ; where ;; codex
// why ; codex ;; Show me the copy this PC can actually find. //
commands ; doctor ;;
ƒin.

STERT ; update ;; codex
commands ; updateme ;;
ƒin.
```

`commands ; doctor ;;` is an application binding of an existing statement shape.
Notes never request execution. Whole-plan eligibility, exact source lines and
preview remain. Legacy `STERT ; ERPDERT ;; codex` retains its original update
meaning as a compatibility input; generated commands/examples use current names.

## Architecture and alternatives

Choose a shared application catalog and typed inspection/operation records.
Command-only aliases would leave UDL and source-connected review inconsistent.
Independent where/update scanners would eventually disagree about the same copy.
A general plugin framework would not itself prove another working application
flow. The shared catalog, discovery adapters, manager adapter and typed dispatcher
provide concrete extension boundaries exercised by the two commands now.

Rename active .NET namespaces/projects, executable, launchers and current help to
DERT. Keep MER as the composition engine's name. Preserve original documents,
historical records and existing recovery files. Existing `.erpdert` repair/draft
storage remains a compatibility format so a rename cannot strand recovery.
Use `DERT_MOTION` with the old environment name as a fallback.

Where's evidence distinguishes PowerShell external PATH order, registry-reported
install locations, verified package roots and known adjacent data folders. A
folder-name match is labeled as such; two launchers for one package are one
installation. Multiple distinct copies indicate possible shadowing, not proven
damage. Folder sizes are measured with bounded, cancellable traversal, explicit
partial totals, no network paths and no traversal through directory links.
An inaccessible location remains visible as missing evidence. Discovery launches
no application or registry uninstall command and never reads credential contents.

The presentation is one connected location view, with exact copyable paths and
provenance, compact/wide composition, plain/reduced-motion parity and a retained
complete record. Animation follows actual discovery/measurement/check events.

## Doctor and effects

The existing npm rehearsal is evidence for planning, not an existing executor.
Build the narrow npm repair transaction behind the same adapter: exact discovered
prefix, matching Node/npm, pinned package/version, manager inventory, snapshot
checks, explicit approval, uninstall, reinstall and post-install verification.
Unsupported managers explain the missing repair capability. Never select another
npm from PATH or delete a config/data folder to repair an installation.

The proposal binds executable paths, selected installation, relevant original
bytes and exact requests. Recheck before changes; changed evidence refuses an
old approval. Keep a durable operation receipt before mutation and after each
phase. Failed uninstall stops installation; failed install records that the copy
may be absent/partial and provides its exact recovery command. Do not claim an
automatic rollback or revert unrelated global packages. This transaction is not
atomic. Dry runs and test runners cannot be described as successful live repairs.

The user's request authorizes implementing this flow, not uninstalling their
working Codex during development. Exercise writes only in disposable test-owned
prefixes. Verify current official npm behavior when developing the adapter.

## Adverse cases and evidence

Test ordinary prose/notes, unfinished source, invalid application names, unknown
flags, duplicate switches, aliases, mixed-case names, quoted paths, PATH ambiguity,
unreadable locations, redirected folders, stale source and stale installation,
changing files during size traversal, cancellation and repeated review. Captured
source and application checks have distinct timestamps. Refresh cannot inherit
older success; source repair invalidates attached application decisions.

Tests own their input files. Inspect actual wide/narrow composition, exercise the
published DERT executable and native Notes launcher, and run source-only suites.
Record local-machine observations separately from fixtures and npm runtime probes.
Clean-account installation and arbitrary-manager doctoring remain broader work.

## Delivered implementation and review, 2026-09-09

The implementation uses `ApplicationCatalog` and `ApplicationRequest` for the
shared option/action, `CommandPathScanner`/`ApplicationLocator` for local evidence,
`NpmUpdateRehearsal` for manager checks, and `DoctorService` for saved proposal and
transaction boundaries. CLI and `DertOperationPlan` bind into those same services.
`LocationConnection`, `LocationCompositor` and the existing MER document compositor
retain source relationships and the established palette. `LocationMotion` and
`DoctorMotion` publish actual scan/process boundaries; they add no delay or
invented percentage. Final output remains independent of animation.

Location names are literal, including spaces, Unicode letters and parentheses.
They are not shell fragments or fuzzy search expressions. Package capability is
explicitly limited to the supported Codex adapter. `--path` selects a doctor or
update-rehearsal copy; unsupported option combinations are rejected.

Original `docs/archive/original.md`, `docs/WHO-WE-ARE.md` and `RERDMERR.DERT`
were not modified. Original ERPDERT receiver input, legacy motion fallback and
`.erpdert` source-recovery storage remain compatible. Existing ERP discovery,
update and binding diagnostic identifiers remain stable; current command prose
and active project names use DERT.

Saved proposals bind source bytes (when source-originated), selected route, Node,
canonical and alias npm inputs, launcher slots, package metadata, entrypoint and
exact requests. Loading verifies them before any process. Regular canonical
package paths remain required; an NVM-style local prefix junction is supported
by retaining its resolved target and checking it again across transaction phases.
Retargeting that junction or changing npm after uninstall stops before install.

Independent reviews found and corrected default MER selection retargeting,
cross-drive folder grouping, interrupted-query status, PowerShell argument
quoting and the alias/canonical npm snapshot distinction. Regression tests cover
each. Incomplete PATH discovery requires an explicit copy selection. The final
read-only review reported no remaining blockers in the reviewed scope.
