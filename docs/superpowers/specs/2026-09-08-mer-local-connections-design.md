# From a written request to the copy on this PC

Working recommendation, 2026-09-08. Authority: the user's instruction to continue
development and polish to an impressive standard; the original `STERT ; ERPDERT
;; codex` use case; the source-window correction and its restraint requirement.
The command names and layout below are implementation choices, not new grammar.

## Person, action, and visible result

An author sees a tool request in their own notes and wants to know what it would
find on this PC. The source stays in its document window. `next` and `prev` move
through actual findings, contextual notes, and supported requests. The prompt
names the next destination; `at <line>` remains available for arbitrary source.
Selecting a request explains its real application meaning before any inspection.

At `STERT ; ERPDERT ;; codex`, `probe` performs the existing local discovery.
Its result attaches to that exact source line: launchers, their package identity,
version, Node and adjacent npm evidence. `copy 2` inspects a second installation
from that same captured report. Multiple copies and unknown launchers remain
explicit. `details` exposes full paths and every issue. Reading notes requires
none of these actions.

## Alternatives and recommendation

A new shell command to copy would break the connection to the source the person
is reading. Automatically probing all named notes would invent operational
meaning and perform unexpected work. A full-screen dashboard would change the
inline delivery. The chosen integration connects the existing operation binder,
local discovery adapter and source compositor, on an explicit `probe` action.
One attached provenance diagram carries the depth; extra boxes do not.

## Meaning and effects

The existing DertOperationPlan owns application binding. A `// why ; codex ;;`
note is context, never an instruction. The entire plan must remain eligible;
unsupported later statements and unfinished structure block inspection. Update
requests are explained without substituting discovery or starting a rehearsal.

Before probing, compare the file's bytes with the captured source. A changed or
unreadable file refuses the new inspection while preserving the old document.
Discovery reads local PATH launchers and package metadata; it starts no programs,
performs no network request and edits nothing. Selecting another copy reuses
that recorded inspection. A repeated `probe` explicitly inspects again.

Inspection results have their own timestamp and evidence, separate from the
completed source-analysis journal. The diagram cannot claim a manager owns the
installation merely because an npm launcher is nearby. PATH results describe
external command routes, without claiming to resolve aliases or functions.
Source spelling, notes and source ranges remain unchanged.

## Adverse and repeated use

Unknown launchers, missing dependencies, unreadable PATH entries, multiple
installations and zero results are useful results with clear limitations. The
attached summary discloses outstanding issues; full detail retains all evidence.
Invalid navigation leaves selection and captured results intact. Endpoints do
not silently wrap. Narrow windows keep the core result and disclose omitted
details. Reduced motion and plain mode preserve meaning. Redirected output does
not read commands unless `--review` explicitly requests scripted review.

## Scope and evidence to inspect

This increment integrates local discovery into the existing source window and
improves meaningful navigation. Package-manager execution, update approval,
in-window repair writes, additional tool adapters and editor integration remain
separate work. No new package-manager behavior is implemented or inferred.

Validate via fixtures owned by tests: navigation, actual discovery metadata,
multiple copies, stale source, ambiguous notes, blocked chains, missing tools,
Unicode/control-safe paths, and complete recorded evidence. Then inspect wide
and narrow rendered windows and exercise the published CLI with real local PATH
inspection. Evidence records must distinguish controlled fixtures, local machine
observations and user judgment.

## Inspection record

The implementation adds source-margin ownership traces and emphasizes changed
title-rule marks. Independent review caught four evidence gaps: omitted binding
blockers in details, an unsettled cancellation view, an unqualified first-match
claim after an incomplete search, and omitted per-launcher dependencies. These
were corrected; focused regression tests cover the first-match and blocker cases.
Cancellation now settles the attached view and stops discovery between filesystem
reads. All copy navigation continues to use the retained inspection.

Actual local inspection found three launchers for one identified package and
reported two inaccessible PATH entries in this sandbox. It therefore labels the
first observed match as an incomplete search. Wide/narrow rendered frames were
inspected; these are actual compositor output, not OS screenshots. Controlled
fixtures separately exercise two copies, unknown launchers, blocked requests,
unchanged bytes, and stale source. Final verification is recorded in the changelog.
